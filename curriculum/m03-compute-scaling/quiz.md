**1.** TodayOrder의 이미지 썸네일 생성 작업은 S3에 쌓인 원본을 읽어 처리하며, 작업이 중간에 끊겨도 다시 큐에 넣으면 된다. 매일 수천 건이 들어온다. 가장 비용 효율적인 컴퓨트 구매 옵션은?

- A. 온디맨드 인스턴스
- B. 스팟 인스턴스를 여러 유형·여러 AZ로 분산
- C. 3년 Standard RI
- D. 전용 호스트

<details><summary>정답과 해설</summary>

**B.** 중단을 견디는(재시도 가능한) 작업이고 "가장 비용 효율적"을 요구하므로 최대 90% 할인되는 스팟이 맞다. 여러 유형·AZ로 분산하면 중단 영향이 줄어든다. A는 중단은 없지만 비싸다. C는 꾸준히 도는 기준 부하용 약정이라 들쭉날쭉한 배치에는 낭비가 생긴다. D는 라이선스·규정 요건이 있을 때 쓰는 가장 비싼 옵션이다.
</details>

**2.** 회사가 내년에 API 서버 일부를 EC2에서 Fargate로, 이벤트 처리를 Lambda로 옮길 계획이다. 지금부터 3년 동안 컴퓨트 비용을 꾸준히 할인받고 싶다. 무엇을 사야 하나?

- A. EC2 Instance Savings Plans
- B. Standard 예약 인스턴스
- C. Compute Savings Plans
- D. 온디맨드 용량 예약

<details><summary>정답과 해설</summary>

**C.** Compute Savings Plans는 인스턴스 패밀리·리전과 상관없이 EC2, **Fargate, Lambda** 사용량에 할인을 적용한다. A는 한 리전의 한 EC2 패밀리에만, B는 EC2 유형에 묶여 Fargate·Lambda로 옮기면 할인이 사라진다. D는 용량 보장일 뿐 할인이 없다.
</details>

**3.** 연말 행사 당일(하루) us-east-1a에서 m7i.xlarge 30대를 **반드시** 띄울 수 있어야 한다. 장기 약정은 원하지 않는다. 무엇을 쓰나?

- A. 리전 범위 Standard RI
- B. 온디맨드 용량 예약을 행사 기간 동안만 만든다
- C. 스팟 인스턴스 요청
- D. 클러스터 배치 그룹

<details><summary>정답과 해설</summary>

**B.** 온디맨드 용량 예약은 약정 없이 특정 AZ의 용량을 보장하고, 필요 없어지면 취소한다(만들어 둔 동안은 사용 여부와 관계없이 과금). A는 1년 이상 약정이고 리전 RI는 용량을 보장하지 않는다. C는 용량이 없으면 뜨지 않고 중단될 수도 있다. D는 배치 방식일 뿐 용량 보장이 아니며 오히려 용량 부족 오류가 나기 쉽다.
</details>

**4.** 운영 중인 PostgreSQL 서버가 gp2 500 GiB 볼륨에서 I/O 대기가 길다. 볼륨 크기는 충분하고, 비용을 늘리지 않거나 줄이면서 IOPS를 올리고 싶다. 서비스 중단도 피하고 싶다. 가장 알맞은 조치는?

- A. 볼륨을 gp3로 변경하고 필요한 만큼 IOPS를 프로비저닝한다(Elastic Volumes)
- B. 스냅샷을 떠서 io2 볼륨으로 복원한 뒤 교체한다
- C. 볼륨 크기를 2 TiB로 늘려 gp2 기준 IOPS를 올린다
- D. st1로 바꿔 처리량을 높인다

<details><summary>정답과 해설</summary>

**A.** gp3는 크기와 별개로 IOPS를 올릴 수 있고, 같은 크기면 gp2보다 GiB당 싸며, 유형 변경은 연결된 채로(무중단) 된다. B는 중단이 생기고 io2는 훨씬 비싸다(지연 요구가 극단적일 때의 선택). C는 쓰지 않는 용량 비용이 늘어난다. D는 HDD라 DB의 작은 랜덤 I/O에 맞지 않고 부트 볼륨으로도 못 쓴다.
</details>

**5.** 보안 감사에서 "모든 새 EBS 볼륨이 암호화되도록 보장하고, 기존 암호화 안 된 데이터 볼륨도 암호화하라"는 지적을 받았다. 올바른 조합은?

- A. 기존 볼륨에 `modify-volume --encrypted`를 실행하고, 계정에 SCP를 건다
- B. 리전의 EBS 기본 암호화를 켜고, 기존 볼륨은 스냅샷 → 암호화 복사 → 새 볼륨으로 교체한다
- C. 인스턴스 안에서 LUKS로 디스크를 암호화한다
- D. S3 기본 암호화를 켠다(스냅샷이 S3에 저장되므로)

<details><summary>정답과 해설</summary>

**B.** EBS 기본 암호화는 이후 만드는 볼륨을 자동으로 암호화하고, 기존 볼륨은 그 자리에서 암호화할 수 없어 스냅샷을 암호화하며 복사한 뒤 새 볼륨을 만들어 교체한다. A: 기존 볼륨을 직접 암호화하는 옵션은 없다. C는 OS 수준 암호화라 스냅샷·관리 키 통합 같은 EBS 암호화의 이점이 없고, 요구한 "새 볼륨 보장"도 못 한다. D: 스냅샷이 저장되는 곳은 사용자 버킷이 아니라 S3 설정과 무관하다.
</details>

**6.** Cassandra 클러스터 노드 24대를 한 리전에 배치한다. 랙 단위 하드웨어 장애가 여러 복제본을 동시에 날리지 않도록 하고, Cassandra가 각 노드의 물리적 위치(어느 묶음인지)를 알 수 있어야 한다. 어떤 배치 그룹인가?

**C.** 파티션 배치 그룹은 파티션마다 다른 랙 묶음을 쓰고, 인스턴스가 어느 파티션에 있는지 보여 줘 토폴로지 인식 복제에 쓸 수 있다. A는 한 AZ에 촘촘히 모아 오히려 동시 장애 위험을 키운다. B는 AZ당 7대까지라 24대를 담기 어렵고 파티션 정보도 없다. D는 물리 배치를 통제하지 못한다.

**7.** 오래된 결제 모듈의 소프트웨어 라이선스가 **MAC 주소**에 묶여 있다. 서버가 고장 나면 예비 서버로 빨리 넘기고 싶다. 가장 간단한 방법은?

- A. 탄력적 IP를 예비 서버에 다시 연결한다
- B. 라이선스용 보조 ENI를 만들어 붙여 두고, 장애 시 떼어 예비 서버에 붙인다
- C. 같은 AMI로 예비 서버를 띄운다
- D. 인스턴스를 최대 절전시켰다가 다른 AZ에서 시작한다

<details><summary>정답과 해설</summary>

**B.** 보조 ENI는 프라이빗 IP와 **MAC 주소**를 가진 채 같은 AZ의 다른 인스턴스로 옮길 수 있다. A는 공인 IP만 옮긴다(MAC은 그대로 바뀐다). C는 새 ENI가 생겨 MAC이 달라진다. D: 최대 절전은 같은 인스턴스를 재개하는 기능이고 다른 AZ로 옮길 수 없다.
</details>

**8.** 관리자 대시보드 서버는 켜고 나서 캐시를 데우는 데 15분이 걸린다. 밤에는 비용을 아끼려 끄고 싶지만 아침에 바로 쓰고 싶다. 서버는 이미 6개월째 운영 중이다. 맞는 설명은?

- A. 지금 인스턴스에 최대 절전을 켜고 밤마다 `stop --hibernate`를 실행하면 된다

**9.** 실시간 게임 서버는 UDP를 쓰고, 클라이언트 앱에 하드코딩할 **고정 IP**가 필요하며, 지연이 극도로 낮아야 한다. 어떤 로드 밸런서인가?

- A. Application Load Balancer
- B. Network Load Balancer (AZ마다 EIP)
- C. Gateway Load Balancer
- D. Classic Load Balancer

<details><summary>정답과 해설</summary>

**B.** NLB는 L4(TCP/UDP)에서 매우 낮은 지연으로 동작하고 AZ마다 고정 IP(EIP 지정 가능)를 준다. A는 HTTP 계열 L7이며 고정 IP가 없다. C는 방화벽 같은 어플라이언스를 끼워 넣는 용도다. D는 이전 세대라 새 설계에 쓰지 않는다.
</details>

**10.** NLB 뒤에 us-east-1a 대상 2대, us-east-1b 대상 8대가 있다(기본 설정). 1a의 두 대가 과부하를 호소한다. 가장 적은 변경으로 고르게 하려면?

- A. 스티키 세션을 켠다
- B. 교차 영역 로드 밸런싱을 켠다

**B.** NLB는 교차 영역이 기본 꺼짐이라 각 AZ의 노드가 자기 AZ 대상에만 나눈다. 트래픽 절반을 1a의 두 대가 받는다. 켜면 열 대가 고르게 받는다(AZ 간 전송 요금이 생길 수 있다). A는 쏠림을 더 키울 수 있다. C는 대상을 뺄 때의 대기 시간이라 분산과 무관하다. D는 비용만 늘리는 우회책이다.

**11.** 쇼핑몰 ALB 뒤 서버들이 로그인 세션을 각자 메모리에 둔다. 오토 스케일링으로 축소될 때마다 일부 사용자가 로그아웃된다. 장기적으로 가장 좋은 해결책은?

- A. ALB 스티키 세션의 쿠키 기간을 7일로 늘린다

**13.** ASG(헬스 체크 유형: EC2)의 인스턴스에서 애플리케이션 프로세스가 죽었다. ALB 대상 그룹은 그 인스턴스를 unhealthy로 표시했지만 ASG는 교체하지 않는다. 원인과 해결은?

- A. 쿨다운 중이라서다. 쿨다운을 줄인다
- B. EC2 헬스 체크는 인스턴스 상태만 보기 때문이다. ASG 헬스 체크 유형을 ELB로 바꾼다
- C. 수명 주기 후크가 없어서다. 종료 후크를 추가한다
- D. 최소 용량이 너무 작아서다. 최소 용량을 늘린다

</details>

**15.** DynamoDB 테이블의 읽기 용량과 ECS 서비스의 태스크 수를 지표에 맞춰 자동으로 조정하려 한다. 무엇을 쓰나?

- A. Amazon EC2 Auto Scaling
- B. Application Auto Scaling
- C. Elastic Beanstalk
- D. EC2 Fleet

<details><summary>정답과 해설</summary>

**B.** Application Auto Scaling은 ECS 태스크 수, DynamoDB 용량, Aurora 복제본 수처럼 EC2가 아닌 확장 가능한 리소스를 조정한다(여러 서비스를 한 계획으로 묶어 보려면 AWS Auto Scaling 콘솔). A는 EC2 인스턴스 그룹 전용이다. C는 웹 앱 배포 PaaS다. D는 여러 유형·구매 옵션으로 EC2 용량을 한 번에 띄우는 기능이다.
</details>
