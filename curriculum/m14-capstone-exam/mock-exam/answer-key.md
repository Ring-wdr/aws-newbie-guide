## 해설

읽는 법: **정답 근거** → **오답이 틀린 이유**(보기마다) → **복습**(이 커리큘럼의 레슨). 링크는 이 파일 기준 상대 경로다.

### 1번 — C · D2(2.1) · 단일

**정답 근거**: 문제의 핵심은 "하위 시스템이 느리면 주문 접수까지 멈춘다"는 강결합이다. SQS 큐를 사이에 두면 API는 큐에 넣는 순간 응답하고(접수 유실 없음 — 메시지는 큐에 최대 14일 보존), 워커는 자기 속도로 처리한다. 큐 길이(`ApproximateNumberOfMessagesVisible`) 또는 "인스턴스당 백로그"에 맞춰 워커 ASG를 조정하면 처리량도 따라온다. "몇 분 늦어도 된다"는 비동기 처리 허용 신호다.
- A ✗ 스레드를 늘려도 하위 시스템이 느린 동안 대기 스레드가 함께 늘 뿐이다. 수직 확장은 결합을 끊지 못한다.
- B ✗ ALB는 요청을 분산할 뿐 버퍼링하지 않는다. 하위 시스템이 느리면 그대로 타임아웃이 난다.
- D ✗ SNS는 메시지를 보관하지 않는다. HTTP 구독자가 느리거나 죽으면 재시도 정책이 끝난 뒤 메시지를 잃을 수 있어 "유실 금지"를 만족하지 못한다(구독 DLQ를 붙여도 처리 속도 조절 수단은 아니다).

**복습**: [M06-01 왜 디커플링인가](../../m06-integration-messaging/01-why-decoupling.md), [M06-02 SQS](../../m06-integration-messaging/02-sqs.md), [M03-06 Auto Scaling](../../m03-compute-scaling/06-auto-scaling.md)

### 2번 — A · D1(1.1) · 단일

**정답 근거**: OIDC 연동이면 장기 키가 아예 없다. GitHub가 발급한 OIDC 토큰을 STS `AssumeRoleWithWebIdentity`로 바꿔 짧은 수명의 임시 자격 증명을 받고, 역할 신뢰 정책의 `token.actions.githubusercontent.com:sub` 조건(예: `repo:org/repo:ref:refs/heads/main`)과 `aud` 조건으로 "그 저장소의 그 브랜치"만 허용한다.
- B ✗ 교체 주기를 줄여도 여전히 장기 키다. 유출되면 다음 교체까지 쓰인다.
- C ✗ 키를 어디에 두든 장기 키라는 사실은 같다. 게다가 GitHub에서 Secrets Manager를 읽으려면 또 다른 자격 증명이 필요하다(닭과 달걀).
- D ✗ SSH 키라는 또 다른 장기 비밀과 인터넷에 열린 22번 포트를 만든다. 공격 면이 오히려 넓어진다.

**복습**: [M01-06 자격 증명 연동](../../m01-iam-identity/06-federation-and-directory.md), [M01-04 역할과 STS](../../m01-iam-identity/04-roles-and-sts.md) (lab07: GitHub Actions 역할)

### 3번 — B · D3(3.3) · 단일

**정답 근거**: DAX는 DynamoDB 전용 인메모리 캐시로, 캐시 적중 시 마이크로초 단위 읽기를 제공하고 DynamoDB API와 호환되어 클라이언트만 바꾸면 된다(코드 변경 최소). 같은 항목에 읽기가 몰리는 "핫 키" 문제도 캐시가 흡수한다. 몇 초 늦은 반영 허용 = 최종 일관 캐시 허용.
- A ✗ 용량 모드는 처리량 관리 방식일 뿐 지연 시간을 마이크로초로 줄이지 못한다.
- C ✗ 구조가 크게 바뀌는 큰 코드 변경이고, 상품 정보 갱신 때마다 동기화·무효화를 직접 해야 한다.
- D ✗ 강력한 일관성 읽기는 오히려 비용이 두 배이고 지연은 줄지 않는다. DAX도 강력한 일관성 읽기는 캐시하지 않는다.

**복습**: [M05-06 캐시](../../m05-databases/06-caching-elasticache.md), [M05-05 DynamoDB 심화](../../m05-databases/05-dynamodb-advanced.md)

### 4번 — D · D4(4.2) · 단일

**정답 근거**: Compute Savings Plans는 시간당 사용 금액을 약정하면 **인스턴스 패밀리·크기·리전·OS와 무관하게 EC2, Fargate, Lambda**에 할인이 적용된다(최대 약 66%). 패밀리 변경(Graviton 전환)과 리전 변경 가능성, 세 서비스 혼용이 모두 이 답을 가리킨다.
- A ✗ Standard RI는 특정 인스턴스 속성에 묶인다. 패밀리를 바꾸면 할인이 사라지고, Fargate·Lambda에는 적용되지 않는다.
- B ✗ EC2 Instance Savings Plans는 한 리전의 한 패밀리에 묶인다(할인 폭은 더 크지만). Graviton 패밀리로 바꾸거나 Fargate·Lambda를 쓰면 적용되지 않는다.
- C ✗ 꾸준한 상시 워크로드(API 등)를 중단 가능한 스팟으로 모두 옮기는 것은 가용성 요구를 깬다. 스팟은 중단 허용 워크로드용이다.

**복습**: [M03-02 구매 옵션](../../m03-compute-scaling/02-purchase-options.md), [M13-02 컴퓨트 비용](../../m13-cost-optimization/02-compute-cost.md)

### 5번 — B · D1(1.2) · 단일

**정답 근거**: S3 게이트웨이 엔드포인트는 라우팅 테이블에 S3 접두사 목록 경로를 넣어 트래픽을 AWS 네트워크 안에서 보낸다(인터넷·NAT 불필요, 무료). 버킷 정책에서 `aws:SourceVpce`(또는 `aws:SourceVpc`)가 다르면 Deny하면 "그 VPC에서 온 요청만"이 강제된다.
- A ✗ NAT 게이트웨이를 거치면 트래픽이 인터넷 경로(퍼블릭 엔드포인트)로 나간다. ①을 어긴다.
- C ✗ Transfer Acceleration은 먼 곳에서의 업로드를 엣지 경유로 빠르게 하는 기능이다. 인터넷 경로이고 VPC 제한과 무관하다. `SecureTransport`는 HTTPS 강제일 뿐이다.
- D ✗ 보안 그룹은 트래픽을 허용·차단할 뿐 경로를 만들지 않는다. 엔드포인트가 없으면 여전히 NAT/인터넷 경로가 필요하고, 버킷 쪽 제한도 없다.

**복습**: [M02-05 VPC 엔드포인트](../../m02-vpc-networking/05-vpc-endpoints.md), [M04-04 S3 보안](../../m04-storage/04-s3-security.md)

### 6번 — B, D · D2(2.2) · 복수

**정답 근거**: AZ 장애를 견디려면 ① 진입점(ALB)이 여러 AZ의 서브넷에 있어야 하고(B), ② 인스턴스가 여러 AZ에 있으며 비정상 인스턴스를 교체해야 한다(D). ASG 헬스 체크를 **ELB**로 해야 "인스턴스는 running이지만 앱은 500"인 경우도 비정상으로 보고 교체한다(EC2 헬스 체크는 인스턴스 상태만 본다).
- A ✗ 클러스터 배치 그룹은 한 AZ에 몰아넣는다. 가용성과 정반대다.
- C ✗ 더 큰 인스턴스 한 대는 여전히 단일 장애점이다.
- E ✗ EBS 다중 연결은 **같은 AZ** 안에서만 되고(io1/io2), 클러스터 인식 파일 시스템이 필요하다. AZ 간 공유 수단이 아니다.

**복습**: [M03-05 로드 밸런서](../../m03-compute-scaling/05-load-balancers.md), [M03-06 Auto Scaling](../../m03-compute-scaling/06-auto-scaling.md), [M12-01 가용성과 SPOF](../../m12-resilience-dr-migration/01-availability-and-spof.md)

### 7번 — A · D3(3.1) · 단일

**정답 근거**: FSx for Lustre는 HPC·ML용 고성능 병렬 파일 시스템으로 밀리초 미만 지연과 매우 높은 처리량을 내고, S3 버킷과 데이터 저장소 연결을 맺어 S3 객체를 파일로 보이게 하고 결과를 S3로 내보낼 수 있다. "S3 데이터 + HPC + POSIX 공유"의 정석이다.
- B ✗ EFS도 공유 POSIX 파일 시스템이지만 HPC 수준의 지연·처리량에는 Lustre가 맞고, S3 연동 기능이 없다. 최대 I/O 모드는 이전 세대 설정이다.
- C ✗ EBS는 한 인스턴스(또는 같은 AZ의 다중 연결)용 블록 스토리지라 수백 대가 같은 파일 시스템을 공유할 수 없다.
- D ✗ File Gateway는 온프레미스에서 S3를 NFS/SMB로 쓰기 위한 하이브리드 서비스다. 캐시 크기에 묶이고 HPC 성능을 내지 못한다.

**복습**: [M04-06 파일 스토리지](../../m04-storage/06-file-storage-efs-fsx.md)

### 8번 — C · D1(1.3) · 단일

**정답 근거**: SSE-KMS + 고객 관리형 키는 ① 키 사용이 CloudTrail에 기록되고 ② 키를 비활성화하면 그 키로 암호화된 객체를 복호화할 수 없으며 ③ 키 정책으로 키 관리자(관리 동작)와 사용자(Encrypt/Decrypt)를 분리할 수 있다. S3와 통합되어 운영 부담도 작다.
- A ✗ SSE-S3는 키를 S3가 관리해 키 사용 감사도, 키 비활성화도, 권한 분리도 할 수 없다.
- B ✗ SSE-C는 키를 고객이 매 요청마다 보내야 해 키 보관·배포 부담이 크고 감사 기록도 남지 않는다. 2026-04부터 새 범용 버킷에서는 기본으로 차단된다.
- D ✗ CloudHSM은 단일 테넌트 HSM이 꼭 필요할 때의 선택이다. 클러스터 운영·클라이언트 측 암호화 구현 부담이 커서 "운영 부담 최소"와 맞지 않는다.

**복습**: [M09-01 KMS](../../m09-security-encryption/01-kms.md), [M04-04 S3 보안](../../m04-storage/04-s3-security.md)

### 9번 — A · D4(4.1) · 단일
