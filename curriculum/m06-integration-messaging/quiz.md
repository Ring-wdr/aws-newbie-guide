**1.** TodayOrder의 주문 API는 주문 저장 후 알림 서버를 동기로 호출한다. 알림 서버가 장애 나면 주문도 실패한다. 알림은 몇 분 늦어도 된다. 가장 적은 변경으로 주문 성공률을 지키는 방법은?

- A. 알림 서버를 더 큰 인스턴스로 바꾼다
- B. 주문 API가 SQS 큐에 알림 요청을 넣고, 알림 워커가 큐에서 꺼내 처리한다
- C. 주문 API에 재시도 로직을 넣어 알림 서버를 최대 5번 호출한다
- D. 알림 서버 앞에 ALB를 둔다

<details><summary>정답과 해설</summary>

**B.** 큐가 생산자와 소비자를 분리해 알림 서버 장애가 주문에 전파되지 않고, 메시지는 큐에 남아 나중에 처리된다. A는 장애 자체를 없애지 못한다. C는 응답을 더 느리게 만들고 장애 중엔 결국 실패한다. D는 여러 대에 분산할 뿐 동기 결합은 그대로다.
</details>

**2.** 이미지 썸네일 워커가 SQS에서 메시지를 받아 처리하는 데 평균 90초가 걸린다. 같은 이미지가 두세 번 처리되는 일이 자주 생긴다. 원인과 해결로 가장 알맞은 것은?

- A. 롱 폴링을 끄면 된다
- B. FIFO 큐로 바꾸면 한 번만 처리된다
- C. 메시지 보존 기간을 14일로 늘린다
- D. 큐의 가시성 타임아웃(기본 30초)이 처리 시간보다 짧다. 처리 시간보다 넉넉히 늘린다

<details><summary>정답과 해설</summary>

**D.** 처리 중 가시성 타임아웃이 끝나 메시지가 다시 보이고 다른 워커가 같은 작업을 시작한다. A는 빈 응답과 무관하다. C는 보관 기간일 뿐 재등장과 무관하다. B: FIFO도 가시성 타임아웃이 끝나면 같은 메시지를 다시 전달한다(중복 제거는 **전송** 시점의 중복만 막는다).
</details>

**3.** 워커들이 빈 응답을 대량으로 받고 있고 SQS 요청 비용이 예상보다 높다. 무엇을 바꿔야 하는가?

- A. 큐의 `ReceiveMessageWaitTimeSeconds`를 1~20초로 설정해 롱 폴링을 쓴다
- B. `DelaySeconds`를 늘린다
- C. 가시성 타임아웃을 0으로 줄인다
- D. 큐를 여러 개로 나눈다

<details><summary>정답과 해설</summary>

**A.** 롱 폴링은 메시지가 오거나 대기 시간이 끝날 때까지 기다려 빈 응답과 요청 수를 줄인다. B는 메시지 전달을 늦출 뿐이다. C는 중복 처리를 늘린다. D는 요청 수를 오히려 늘린다.
</details>

**4.** 주문 상태 변경 이벤트(생성→결제→배송)를 처리하는데, **같은 주문**의 이벤트는 반드시 순서대로, 중복 없이 처리돼야 한다. 주문 수가 많아 처리량도 필요하다. 가장 알맞은 설계는?

- A. 표준 큐 + 소비자 1대
- B. FIFO 큐, `MessageGroupId` = 고정 문자열 `"orders"`
- C. FIFO 큐, `MessageGroupId` = 주문 ID
- D. SNS 표준 토픽 → 표준 큐

<details><summary>정답과 해설</summary>

**C.** FIFO는 그룹 안에서 순서를 지키고, 그룹이 다르면 병렬 처리된다. 주문 ID를 그룹으로 쓰면 주문별 순서와 처리량을 모두 얻는다. A는 순서·중복을 보장하지 않고 처리량도 낮다. B는 큐 전체가 한 줄로 처리돼 처리량이 떨어진다. D는 순서·중복 제거가 없다.
</details>

**5.** 정산 큐에 잘못된 통화 코드가 들어간 메시지가 몇 건 섞여, 워커가 계속 실패하며 같은 메시지를 반복 처리한다. 다른 정상 메시지 처리를 보호하고 실패 메시지는 나중에 분석하고 싶다. 무엇을 하는가?

- A. DLQ를 만들고 원본 큐에 재드라이브 정책(maxReceiveCount)을 건다
- B. 메시지 보존 기간을 60초로 줄인다
- C. 워커가 실패 메시지를 바로 삭제하게 한다
- D. 가시성 타임아웃을 12시간으로 늘린다

<details><summary>정답과 해설</summary>

**A.** maxReceiveCount를 넘긴 메시지가 DLQ로 옮겨져 원본 큐 처리를 막지 않고, 원인 분석 후 DLQ 재드라이브로 되돌릴 수 있다. B는 정상 메시지까지 잃을 수 있다. C는 분석 근거를 잃는다. D는 실패 메시지를 숨길 뿐 해결이 아니고 정상 재시도도 늦춘다.
</details>

**6.** SNS 토픽에 SQS 큐를 구독시켰다. `subscribe`와 `publish` 모두 성공했지만 큐에 메시지가 하나도 없다. 큐는 암호화되지 않았다. 가장 먼저 확인할 것은?

- A. 큐의 가시성 타임아웃
- B. SNS 토픽이 FIFO인지
- C. 큐의 리소스 기반 정책이 `sns.amazonaws.com`에 `sqs:SendMessage`를 허용하는지
- D. 주문 API의 IAM 사용자에게 `sqs:ReceiveMessage` 권한이 있는지

<details><summary>정답과 해설</summary>

**C.** SNS가 큐에 넣으려면 큐 정책의 허용이 필요하고, 없으면 오류 없이 전달만 안 된다(lab04에서 실제로 관찰). A는 수신 후의 동작이다. B: 표준 토픽 → 표준 큐는 정상 구성이다. D는 생산자의 수신 권한으로, SNS의 전달과 무관하다. (암호화 큐였다면 KMS 키 정책도 확인 대상이다.)
</details>

**7.** 주문 이벤트를 알림·정산·분석 세 시스템이 **각자** 받아야 하고, 정산은 결제 완료 이벤트만 필요하다. 각 시스템은 자기 속도로 처리한다. 가장 알맞은 구성은?

- A. 큐 하나에 세 시스템의 워커가 함께 붙는다
- B. Amazon Data Firehose로 세 시스템에 보낸다
- C. 주문 API가 세 시스템의 HTTP API를 차례로 호출한다
- D. SNS 토픽 → 시스템별 SQS 큐 3개, 정산 구독에는 필터 정책

<details><summary>정답과 해설</summary>

**D.** 팬아웃 패턴. 각 큐가 소비자별 버퍼가 되고 필터 정책으로 정산은 필요한 이벤트만 받는다. A는 한 메시지를 한 워커만 받으므로 "각자 받기"가 안 된다. C는 동기 결합이다. B: Firehose는 S3·Redshift 등 **적재** 목적지용이지 애플리케이션 팬아웃용이 아니다.
</details>

**8.** 결제 대행사(SaaS)가 보내는 결제 이벤트와 자사 주문 서비스의 이벤트를 한 곳에서 받아, 이벤트 필드 값(금액, 결제 수단)에 따라 서로 다른 대상으로 보내야 한다. 과거 이벤트를 다시 흘려보내는 기능도 필요하다. 무엇을 쓰는가?

- A. Amazon SNS 표준 토픽
- B. Amazon EventBridge (파트너 이벤트 버스 + 사용자 지정 버스, 규칙, 아카이브·재생)
- C. Amazon SQS FIFO
- D. Amazon MQ

<details><summary>정답과 해설</summary>

**B.** SaaS 파트너 이벤트, 내용 기반 규칙, 아카이브·재생은 EventBridge의 기능이다. A는 SaaS 연동·재생이 없다. C는 라우팅이 없다. D는 기존 브로커 프로토콜 이전용이다.
</details>

**9.** 주문 처리 워크플로에서 결제 단계가 PG 일시 장애로 실패하면 잠시 뒤 재시도하고, 카드 거절이면 재시도 없이 고객 알림 단계로 가야 한다. Step Functions 정의로 가장 알맞은 것은?

- A. `Retry: [{ErrorEquals: [States.ALL], MaxAttempts: 3}]` 만 둔다
- B. 결제 Lambda 안에서 `while` 루프로 재시도한다
- C. `Catch: [{ErrorEquals: [States.ALL], Next: 알림}]` 을 맨 위에 두고 그 아래 거절 오류를 둔다
- D. `Retry`에 일시 오류만 지정(지수 백오프), `Catch`에 거절 오류 → 알림 상태, 마지막에 `States.ALL` → 실패 처리

<details><summary>정답과 해설</summary>

**D.** 일시 오류와 업무 오류를 오류 이름으로 나눠 Retry와 Catch에 배치한다(lab06에서 TaskFailed 3건/1건으로 확인). A는 거절도 재시도해 응답만 늦어진다. C는 Catch가 위에서부터 첫 일치를 쓰므로 모든 오류가 States.ALL로 가 버린다. B는 Lambda 실행 시간(비용)과 15분 한도를 소모하고 실행 이력에 남지 않는다.
</details>

**10.** 하루 수백만 건의 IoT 측정값을 받아 5초 이내로 변환해 DynamoDB에 쓰는 짧은 워크플로가 필요하다. 작업은 멱등하다. 비용이 가장 낮은 Step Functions 유형은?

- A. 익스프레스 워크플로
- B. 표준 워크플로
- C. 표준 워크플로 + `.waitForTaskToken`
- D. 분산 Map을 쓰는 표준 워크플로

<details><summary>정답과 해설</summary>

**A.** 짧고(5분 이내) 대량이며 멱등한 작업은 실행 수·시간 기반 과금인 익스프레스가 싸다. B는 상태 전이마다 과금되어 대량에서 비싸다(정확히 한 번 보장이 필요 없는데 비용만 크다). C는 사람/외부 콜백을 기다리는 패턴이다. D는 대량의 배치(S3 객체 등)를 병렬 처리하는 기능으로 이벤트 스트림 처리와 맞지 않는다.
</details>

**11.** 클릭스트림을 실시간 대시보드, 사기 탐지, 데이터 레이크 적재 세 소비자가 같은 데이터로 처리해야 하고, 사기 탐지 모델을 고치면 지난 24시간 데이터를 다시 처리하고 싶다. 수집 계층으로 알맞은 것은?

- A. SQS 표준 큐
- B. SNS 표준 토픽
- C. Kinesis Data Streams
- D. Amazon Data Firehose 단독

<details><summary>정답과 해설</summary>

**C.** KDS는 레코드를 보존 기간 동안 보관해 여러 소비자가 독립적으로, 원하는 위치부터 다시 읽을 수 있다. A는 읽고 지우면 사라지고 재생이 안 된다. B는 보관하지 않는다. D는 목적지 적재용이고 재생·다중 소비자 처리 기능이 없다.
</details>

**12.** Kinesis 스트림을 샤드 2개에서 8개로 늘렸는데도 `ProvisionedThroughputExceededException`이 한 샤드에서만 계속 난다. 파티션 키로 "매장 ID"를 쓰는데, 주문의 80%가 한 대형 매장에서 나온다. 가장 알맞은 조치는?

- A. 샤드를 16개로 더 늘린다
- B. 파티션 키를 주문 ID처럼 값이 고르게 퍼지는 키로 바꾼다(매장 단위 순서 보장은 포기)
- C. 보존 기간을 늘린다
- D. 향상된 팬아웃을 켠다

<details><summary>정답과 해설</summary>

**B.** 같은 파티션 키는 MD5 해시가 같아 항상 같은 샤드로 간다(hot shard). 샤드를 늘려도 그 키는 한 샤드에 몰린다. 다만 이것은 **맞바꿈**이다: 키를 주문 ID(또는 매장 ID + 무작위 접미사)로 바꾸면 한 매장의 레코드가 여러 샤드로 흩어져 **매장 단위 순서 보장을 잃는 대신** 처리량을 얻는다. 매장 단위 순서가 꼭 필요하면 그 매장의 처리량은 샤드 하나의 한도를 넘을 수 없다. A는 같은 이유로 효과가 없다. C는 처리량과 무관하다. D는 **읽기** 처리량을 늘리는 기능이고 이 오류는 쓰기 쪽이다.
</details>
