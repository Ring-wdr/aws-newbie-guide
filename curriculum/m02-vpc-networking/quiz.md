**2.** 주니어 개발자가 서브넷 `todayorder-public-c`를 만들고 "퍼블릭 IP 자동 할당"을 켰다. 이 서브넷에 띄운 인스턴스는 퍼블릭 IP를 받았지만 인터넷에서 접속되지 않는다. SG는 443을 열었고 VPC에 IGW도 연결되어 있다. 가장 가능성 높은 원인은?

- A. 서브넷 이름에 public이 들어가 있지만 AWS가 인식하지 못했다
- B. 서브넷을 어떤 라우팅 테이블에도 연결하지 않아 IGW 경로가 없는 기본(main) 라우팅 테이블이 적용되고 있다
- C. NAT 게이트웨이가 없다
- D. NACL이 상태 저장이라 응답이 막혔다

<details><summary>정답과 해설</summary>

**B.** 퍼블릭 서브넷의 정의는 "적용되는 라우팅 테이블에 `0.0.0.0/0 → igw` 경로가 있다"이다. 명시적으로 연결하지 않은 서브넷은 main 라우팅 테이블을 쓰고, 이 모듈의 설계처럼 main에는 `local`만 있다(lab03 문제 7). A: 이름은 아무 의미가 없다. C: NAT는 프라이빗 서브넷의 아웃바운드용이지 인바운드 접속과 무관하다. D: NACL은 상태 비저장이다(사실관계부터 틀렸다).
</details>

**3.** 주문 API는 두 AZ의 프라이빗 서브넷에서 돈다. 비용을 아끼려고 NAT 게이트웨이를 us-east-1a에 하나만 두고 두 앱 서브넷이 같은 라우팅 테이블로 이 NAT를 쓰게 했다. 이 설계의 문제는?

- A. NAT 게이트웨이는 같은 AZ의 서브넷만 처리할 수 있어 1b의 트래픽은 처음부터 실패한다
- B. us-east-1a에 장애가 나면 1b의 주문 API도 외부 결제 API를 호출하지 못한다
- C. NAT 게이트웨이 하나는 대역폭이 1 Gbps로 고정이라 병목이 된다
- D. 문제없다. NAT 게이트웨이는 리전 서비스라 AZ 장애와 무관하다

<details><summary>정답과 해설</summary>

**B.** (zonal) NAT 게이트웨이는 한 AZ 안에서만 이중화된다. AZ 단위로 독립시키려면 AZ마다 NAT를 두고 AZ별 라우팅 테이블이 같은 AZ의 NAT를 가리키게 한다(lab02의 `app-rt-a → nat-a`, `app-rt-b → nat-b`). 교차 AZ 데이터 전송 요금도 줄어든다. A: 다른 AZ에서도 쓸 수는 있다(그래서 이 실수가 흔하다). C: NAT GW는 5 Gbps에서 시작해 100 Gbps까지 자동 확장한다. D: 기본(zonal) NAT GW는 AZ 리소스다. 여러 AZ로 자동 확장하는 **리전 NAT 게이트웨이**라는 별도 모드가 있지만, 문제의 구성은 zonal이다.
</details>

**4.** 앱 서버가 IPv6 주소로 외부 패키지 저장소에 접속해야 하지만, 인터넷에서 앱 서버로 들어오는 IPv6 연결은 막아야 한다. 무엇을 쓰는가?

**5.** 보안팀이 "특정 국가 대역 `198.51.100.0/24`에서 오는 모든 트래픽을 퍼블릭 서브넷 단계에서 즉시 차단하라"고 요청했다. 가장 알맞은 조치는?

- A. ALB 보안 그룹에 해당 대역의 Deny 규칙을 추가한다
- B. 퍼블릭 서브넷의 NACL에 해당 대역 Deny 규칙을 기존 Allow 규칙보다 **작은 번호**로 추가한다
- C. 퍼블릭 서브넷의 NACL에 해당 대역 Deny 규칙을 번호 32767로 추가한다
- D. 라우팅 테이블에서 해당 대역을 블랙홀로 보낸다

<details><summary>정답과 해설</summary>

**B.** NACL은 번호 순서로 평가하고 처음 일치한 규칙에서 멈춘다. Deny가 `100 allow 443`보다 먼저 평가되도록 90처럼 작은 번호를 준다(lab05 Q1: `90 deny`). A: 보안 그룹에는 Deny 규칙이 없다. C: 32767은 기본 `*` 규칙 번호라 사용자가 쓸 수 없고(`1..32766`), 설령 있어도 100번 Allow 뒤라 효과가 없다. D: 인바운드 출처를 라우팅으로 막는 방법이 아니다(라우팅은 목적지 기준).
</details>

**6.** DB 서브넷에 새 NACL을 붙였다. 인바운드에 "앱 서브넷 `10.0.10.0/24`에서 tcp 5432 Allow"만 넣었고 아웃바운드는 기본값 그대로다. 앱이 DB에 연결하면 어떻게 되는가?

- A. 성공한다. 응답은 자동으로 허용된다
- B. 실패한다. 새 NACL의 아웃바운드는 모두 거부라, DB의 응답(앱 쪽 임시 포트 1024-65535)이 나가지 못한다
- C. 성공한다. 같은 VPC 안이라 NACL이 적용되지 않는다
- D. 실패한다. 인바운드 규칙 번호가 100보다 작아야 한다

<details><summary>정답과 해설</summary>

**B.** 새로 만든 NACL은 인바운드·아웃바운드 모두 `* deny`로 시작하고(lab05 1번), NACL은 상태 비저장이다. 응답이 나갈 아웃바운드 규칙(대상 `10.0.10.0/24`, tcp 1024-65535)이 필요하다(lab05 Q5). A는 보안 그룹의 동작이다. C: NACL은 서브넷 경계를 넘는 모든 트래픽에 적용되며 같은 VPC여도 마찬가지다. D: 번호는 순서만 정한다.
</details>

- A. 피어링은 전이적 라우팅을 지원하지 않는다 → A–C를 직접 피어링하거나, 늘어날 것을 고려해 Transit Gateway로 허브·스포크 구성

**14.** 아래는 `app-a` 서브넷에 적용되는 라우팅 테이블이다. 목적지 `198.18.8.10`(S3 접두사 목록 `pl-e9da6b72` = `198.18.8.0/21` 안)으로 가는 패킷의 다음 홉은?

```
10.0.0.0/16  -> local
0.0.0.0/0    -> nat-000000000000000c1
pl-e9da6b72  -> vpce-00000000000000102
10.20.0.0/16 -> tgw-0000000000000011a
```

- A. `nat-000000000000000c1` — 0.0.0.0/0이 먼저 적혀 있으므로
- B. `vpce-00000000000000102` — 일치하는 경로 중 접두사가 가장 긴 것(/21)
- C. `local`
- D. `tgw-0000000000000011a`

<details><summary>정답과 해설</summary>

**B.** VPC 라우팅은 **최장 접두사 일치**다. `198.18.8.10`에 일치하는 경로는 `0.0.0.0/0`(/0)과 접두사 목록의 `198.18.8.0/21`(/21) 둘이고 /21이 더 구체적이다(lab06·lab07). A: 경로의 적힌 순서는 의미가 없다. C: `10.0.0.0/16`에 속하지 않는다. D: `10.20.0.0/16`에 속하지 않는다.
</details>
