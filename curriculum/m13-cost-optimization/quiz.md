# M13 퀴즈 — 비용 최적화

> 모든 문항은 이 커리큘럼을 위해 새로 만든 문제다. 13문항 중 11문항 이상(80% 이상) 맞히면 통과. 풀 때 [레슨 1의 4단계](./01-billing-and-data-transfer.md#가장-비용-효율적인-문제를-푸는-4단계)를 의식적으로 적용해 보라: 제약 → 삭제 → 숨은 비용 → 최저가.

**1.** TodayOrder의 주문 API는 지난 1년 동안 최소 8대의 EC2가 24시간 돌았고, 점심·저녁에는 20대까지 늘어난다. 내년에는 인스턴스 패밀리를 바꾸고 일부를 Fargate로 옮길 계획이다. 가장 비용 효율적인 구매 전략은?

- A. 20대분을 EC2 Instance Savings Plans 3년으로 약정한다
- B. 8대분을 예약 인스턴스(특정 인스턴스 유형)로 약정한다
- C. 전부 스팟 인스턴스로 운영한다
- D. 8대분을 Compute Savings Plans로 약정하고, 피크는 Auto Scaling 온디맨드로 처리한다

<details><summary>정답과 해설</summary>

**D.** 약정은 바닥(8대)에 맞추고, 패밀리 변경과 Fargate까지 할인되는 것은 Compute Savings Plans다. A는 피크에 맞춘 약정이라 피크가 아닌 시간에 약정 금액을 버리고, 패밀리 고정이라 계획과도 맞지 않는다. C는 주문 API처럼 중단되면 안 되는 서비스에 스팟만 쓰면 회수 시 장애가 난다. B는 유형을 바꾸거나 Fargate로 옮기면 할인을 못 받는다.
</details>

**2.** 매일 밤 2시간 동안 도는 이미지 썸네일 재생성 작업이 있다. 작업은 SQS 큐에서 메시지를 받아 처리하며, 중간에 끊겨도 메시지가 큐에 돌아와 다시 처리된다. 아침 9시 전에만 끝나면 된다. 가장 비용 효율적인 컴퓨트는?

- A. 온디맨드 인스턴스
- B. 3년 전부 선결제 예약 인스턴스
- C. 여러 인스턴스 유형에 분산한 스팟 인스턴스
- D. 전용 호스트

<details><summary>정답과 해설</summary>

**C.** 중단 허용·시작 시간 유연·짧은 실행 = 스팟의 전형. 여러 유형·AZ로 분산하면 회수 위험이 줄어든다. A는 동작하지만 더 비싸다. B는 하루 2시간만 쓰는데 24시간분을 약정하는 셈이다. D는 라이선스·규정 요구가 없으니 가장 비싸기만 하다.
</details>

**3.** 프라이빗 서브넷의 EC2들이 같은 리전의 S3 버킷과 매달 수 TB를 주고받는다. 청구서에서 NAT 게이트웨이 처리 요금이 크다. 애플리케이션 코드 변경 없이 비용을 가장 많이 줄이는 방법은?

- A. S3 게이트웨이 VPC 엔드포인트를 만들어 프라이빗 라우팅 테이블에 연결한다
- B. NAT 게이트웨이를 NAT 인스턴스로 바꾼다
- C. S3 인터페이스 VPC 엔드포인트를 만든다
- D. S3 Transfer Acceleration을 켠다

<details><summary>정답과 해설</summary>

**A.** 게이트웨이 엔드포인트는 무료이고, 라우팅 테이블에 S3 접두사 목록 경로가 추가될 뿐이라 코드가 그대로다. B는 처리 요금은 줄 수 있지만 인스턴스 관리·가용성 부담이 생기고 S3 트래픽이 여전히 NAT를 거친다. C도 NAT를 우회하지만 시간당·GB당 요금이 있어 A보다 비싸다(온프레미스 사설 접근이 필요할 때 쓰는 것). D는 먼 거리의 업로드 가속용이며 추가 요금이 든다.
</details>

**4.** 고객 상담 녹음 파일은 30일 동안은 자주 듣고, 그 뒤 1년 동안은 분쟁이 생기면 **즉시** 들어야 하며(1년에 몇 번), 1년 뒤에는 규정상 7년 보관하되 꺼낼 일은 거의 없고 꺼내도 이틀 안이면 된다. 가장 비용 효율적인 수명 주기 설계는?

- A. Standard → 30일 Glacier Deep Archive → 7년 뒤 삭제
- B. Standard → 30일 Standard-IA → 365일 Glacier Deep Archive → 만료
- C. 전부 Intelligent-Tiering에 7년
- D. Standard → 30일 One Zone-IA → 365일 Glacier Flexible Retrieval

<details><summary>정답과 해설</summary>

**B.** 30일~1년 구간은 "드물지만 즉시" → Standard-IA(Glacier IR도 후보). 1년 이후는 "이틀 안이면 됨" → Deep Archive(표준 검색 12시간 이내, 대량 48시간 이내). A는 1년 구간의 "즉시" 요구를 깬다(Deep Archive는 시간 단위). C는 동작하지만 7년 동안 아카이브 계층을 쓰려면 별도 설정이 필요하고, 패턴을 이미 알고 있으니 규칙이 더 싸다. D는 One Zone-IA가 AZ 하나에만 저장해 규정 보관 데이터의 내구성 요구에 맞지 않고, 7년 구간에는 Deep Archive가 더 싸다.
</details>

**5.** 개발팀이 로그 파일(평균 15 KB, 하루 수천만 개)을 30일 뒤 Standard-IA로 옮기는 수명 주기 규칙을 제안했다. 이 규칙의 비용 효과에 대한 설명으로 옳은 것은?

- A. IA는 128 KB 미만 객체도 128 KB로 과금하고 객체당 전환 요청 요금이 붙어, 오히려 비싸질 수 있다
- B. IA가 GB당 저렴하므로 무조건 절감된다
- C. IA는 최소 보관 기간이 없어 위험이 없다
- D. 작은 객체는 Glacier Deep Archive로 옮기면 해결된다

<details><summary>정답과 해설</summary>

**A.** 15 KB 객체를 128 KB로 과금하면 GB당 단가 이점이 사라지고, 객체 수에 비례한 전환 요청 요금까지 붙는다(레슨 3 워크시트). 실제 S3도 기본적으로 128 KB 미만 객체는 전환하지 않는다. B는 숨은 비용을 무시했다. C: IA는 최소 보관 30일이 있다. D: Glacier 계열은 객체마다 메타데이터 오버헤드가 붙고 전환 요청 요금이 더 비싸 작은 객체에 더 불리하다 — 묶어서 저장하거나 Standard에서 만료시키는 편이 낫다.
</details>

**6.** 재무팀이 "다음 달 예상 지출이 월 예산을 넘을 것 같으면 **미리** 이메일을 받고 싶다"고 한다. 가장 적은 운영 노력으로 충족하는 방법은?

- A. Cost Explorer에서 매일 그래프를 확인한다
- B. CloudWatch에서 EC2 CPU 경보를 만든다
- C. CUR을 S3로 내보내고 Athena 쿼리를 Lambda로 매일 돌린다
- D. AWS Budgets에서 예측(FORECASTED) 임계값 알림이 있는 비용 예산을 만든다

<details><summary>정답과 해설</summary>

**D.** Budgets는 실제(ACTUAL)와 예측(FORECASTED) 임계값 알림을 기본 기능으로 제공한다. A는 사람이 매일 봐야 한다(자동 알림이 아님). C는 동작은 하지만 직접 만들고 운영해야 하는 것이 많다. B는 비용이 아니라 성능 지표다.
</details>

**7.** 여러 부서가 같은 AWS 계정을 쓴다. 각 부서의 월 비용을 나눠 청구(chargeback)하려 한다. 무엇이 필요한가?

- A. 부서마다 IAM 그룹을 만든다
- B. 부서마다 다른 리전을 쓰게 한다
- C. 리소스에 `cost-center` 태그를 붙이고, Billing 콘솔에서 비용 할당 태그로 활성화한 뒤 Cost Explorer·CUR에서 태그로 나눈다
- D. Trusted Advisor 비용 점검을 켠다

<details><summary>정답과 해설</summary>

**C.** 비용을 태그로 나누려면 태그를 붙이고 **활성화**해야 한다. 기본은 활성화 이후 비용부터 반영되고, 지난 기간이 필요하면 관리 계정이 **최대 12개월까지 백필**을 요청할 수 있다(그 기간에 태그가 이미 붙어 있던 리소스만 해당). A의 IAM 그룹은 권한 관리이지 비용 배분 차원이 아니다. B는 리전 선택을 비용 배분에 쓰는 셈이라 지연·규정·운영을 망친다. D는 절감 기회를 점검할 뿐 부서별 배분을 하지 않는다.
</details>

**8.** 회사가 AWS Organizations로 계정 12개를 관리한다. 한 계정이 산 예약 인스턴스가 그 계정에서는 다 쓰이지 않는다. 별도 작업 없이 낭비를 줄이는 것은?

- A. RI를 다른 계정으로 수동 이전해야 한다
- B. 통합 결제의 RI·Savings Plans 할인 공유로 다른 계정의 일치하는 사용량에 할인이 적용된다
- C. RI는 구매한 계정에서만 쓸 수 있으므로 방법이 없다
- D. 모든 계정을 하나로 합쳐야 한다

<details><summary>정답과 해설</summary>

**B.** 통합 결제는 조직 전체를 하나의 결제 단위로 보고, RI·Savings Plans 할인을 다른 계정의 일치하는 사용량에 공유한다(관리 계정에서 계정별로 끌 수 있다). 사용량을 합산해 구간 단가 할인(볼륨 할인)도 받는다. A·D는 필요 없는 작업이고, C는 공유 기능을 모르는 오답이다.
</details>

**9.** 2-AZ에 걸친 API 서버(AZ-a, AZ-b)가 AZ-a의 RDS Multi-AZ 기본 인스턴스와 통신한다. 비용 담당자가 "AZ 간 데이터 전송 요금을 없애려면 API 서버를 모두 AZ-a에 두자"고 한다. 가장 적절한 답변은?

- A. 좋은 생각이다. 비용이 최우선이다
- B. 데이터 전송은 무료이므로 의미가 없다
- C. RDS를 단일 AZ로 바꾸면 AZ 간 요금이 사라진다
- D. 고가용성 요구를 깨므로 받아들일 수 없다. AZ 간 요금은 다중 AZ의 대가이며, RDS Multi-AZ 복제 트래픽 자체는 무료다

<details><summary>정답과 해설</summary>

**D.** 비용 문제도 제약(가용성)이 먼저다. AZ-a 장애 시 API가 통째로 죽는다(단일 장애점, M12). A는 제약을 깨는 보기다. C도 DB의 고가용성을 버린다. B는 틀렸다: AZ 간 전송은 양방향 과금이다(단, Multi-AZ 복제 트래픽은 무료).
</details>

**10.** 간헐적으로만 쓰이는 사내 관리자 도구의 데이터베이스가 있다. 몇 시간 동안 요청이 전혀 없다가 갑자기 몰린다. 관계형 SQL이 필요하다. 가장 비용 효율적인 선택은?

- A. Aurora Serverless v2
- B. 가장 큰 RDS 인스턴스를 3년 예약
- C. EC2에 MySQL을 직접 설치
- D. DynamoDB 프로비저닝 용량 모드

<details><summary>정답과 해설</summary>

**A.** 부하에 따라 용량이 자동으로 늘고 줄어드는 관계형 DB라 간헐적 부하에 맞다(조용할 때 용량을 낮게 유지). B는 쓰지 않는 시간에도 큰 인스턴스 값을 3년 낸다. C는 운영 부담이 크고 꺼 두지 않으면 계속 과금된다. D는 관계형 SQL 요구를 깨고, 프로비저닝 모드는 예측 가능한 부하용이다.
</details>

**11.** 전 세계 고객이 TodayOrder의 상품 이미지(S3 오리진)를 내려받아 인터넷 아웃바운드 요금이 크다. 이미지 다운로드 속도도 개선하고 싶다. 가장 비용 효율적인 방법은?

- A. 각 대륙 리전에 버킷을 만들고 교차 리전 복제
- B. EC2 프록시 서버를 여러 리전에 둔다
- C. S3 앞에 CloudFront 배포를 두고 OAC로 버킷 접근을 제한
- D. S3 Transfer Acceleration을 켠다

<details><summary>정답과 해설</summary>

**C.** S3(AWS 오리진) → CloudFront 전송은 무료이고, 엣지 캐시가 속도와 오리진 요청을 함께 개선한다. A는 저장·복제 요금이 리전 수만큼 늘어난다. B는 컴퓨트와 운영 비용이 추가된다. D는 업로드 등 장거리 **전송** 가속용이고 추가 요금이 있으며 캐싱을 하지 않는다.
</details>

**12.** 신규 서비스를 AWS에 올리기 **전에** 경영진에게 월 예상 비용을 보고해야 한다. 아직 리소스는 하나도 없다. 무엇을 쓰는가?

- A. Cost Explorer 예측
- B. AWS Pricing Calculator
- C. AWS Budgets
- D. Cost and Usage Report

<details><summary>정답과 해설</summary>

**B.** Pricing Calculator는 만들지 않은 아키텍처의 견적을 낸다. A의 예측은 **과거 사용량**을 바탕으로 하므로 사용 이력이 없으면 의미가 없다. C는 이미 나가는 비용의 한도 알림, D는 이미 발생한 사용량의 상세 데이터다.
</details>

**13.** 결제 승인 API는 하루 24시간 `m7i.large` 4대가 꾸준히 돌고, 앞으로 최소 1년은 같은 규모다. 요청 처리 중 인스턴스가 회수되면 결제가 실패하므로 **중단되면 안 된다**. 내년에 인스턴스 패밀리를 바꿀 수도 있다. 가장 비용 효율적인 구매 방법은?

- A. 4대 모두 스팟 인스턴스
- B. 전용 호스트에서 4대 실행
- C. 4대 모두 온디맨드 유지
- D. 4대분 Compute Savings Plans 1년 약정

<details><summary>정답과 해설</summary>

**D.** 꾸준한 사용 + 1년 + 패밀리 변경 가능성 → Compute Savings Plans. 중단되지 않는 일반 용량에 할인을 받는다. A는 가장 싸지만 회수될 수 있어 "중단되면 안 된다" 제약을 깬다 — 가장 싼 보기가 답이 아닌 전형이다. C는 제약은 만족하지만 약정 할인을 놓쳐 더 비싸다. B는 라이선스·규정 요구가 없는데 가장 비싸다.
</details>
