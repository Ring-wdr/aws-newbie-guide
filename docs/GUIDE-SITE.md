# 가이드 사이트 설계 (generative UI 전환)

`curriculum/`의 Markdown 가이드를 **에이전트가 미리 생성·검증한 정적 인터랙티브 사이트**로 보여 주기 위한 설계다. 모듈 내용의 설계는 [CURRICULUM.md](./CURRICULUM.md), 원고 작성 규칙은 [AUTHORING.md](./AUTHORING.md), 역할과 브랜치는 [AGENTS.md](./AGENTS.md)를 따른다. 이 문서는 사이트에만 해당하는 규칙을 정한다.

## 1. 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| "generative UI"의 뜻 | 작성 시점에 에이전트가 생성하고 검증자가 통과시킨 정적 페이지 | 내용이 고정돼야 "실제 실행한 출력만 싣는다"와 독립 검증이 성립한다 |
| 실행 시점 LLM | 범위 밖 | 키·비용·네트워크가 필요해 "계정도 요금도 없이, 오프라인으로"와 충돌한다 |
| Markdown 원고 | 지우지 않는다. 사이트가 빌드되는 **단일 원본** | 사실을 손으로 옮겨 적지 않아야 사이트와 실습이 어긋나지 않는다. GitHub에서 그대로 읽히는 예비 경로가 남는다 |
| 배포 | 시범 단계는 로컬 전용. 공개 배포는 전환 단계에서 저장소 소유자가 명시적으로 승인한 뒤 — 2026-11-14에 승인됐다(조건: VM 시계가 안정된 상태에서 전 모듈 실습 회귀가 통과한 뒤 GitHub Pages로). 배포본도 방문자의 브라우저에서 외부 호스트로 요청을 보내지 않는다 | 새 대외 게시 표면이다 |
| 도구 | Node 도구 허용. `site/` 아래에만 둔다 | 빌드하는 쪽만 필요하고 학습자는 필요 없다 |

아직 정하지 않은 것: 원고 삭제(7장 P6). 맞춤 위젯의 범위는 "모듈마다 핵심 개념 하나"로 정해져 P3에서 만들었고, 실시간 에뮬레이터 상태 패널(7장 P5)은 보류했다.

## 2. 원칙

1. **원고가 원본이다.** 페이지의 모든 사실·명령·출력·정답은 `curriculum/`의 원고, lab·sdk 파일, `tools/probe/results.json`에서 빌드 때 읽는다. 사이트 쪽에 사본을 두지 않는다.
2. **기록된 출력만 보여 준다.** 출력 패널은 원고에 실린 실제 실행 결과를 그대로 재생한다. 실행되는 것처럼 꾸민 터미널, 지어낸 응답은 만들지 않는다(AUTHORING 3장 규칙 1).
3. **밖으로 나가지 않는다.** 빌드 산출물은 외부 리소스를 하나도 불러오지 않는다. 웹폰트·CDN·분석 스크립트·외부 이미지를 쓰지 않는다. 글꼴은 시스템 글꼴 스택이다.
4. **모형은 모형이라고 적는다.** 위젯이 보여 주는 동작이 에뮬레이터나 AWS의 실제 실행이 아니라 설명용 모형이면 화면에 "모형"이라고 표시한다. 위젯의 수치는 코드에 박지 않고 원고(레슨·치트시트의 표)에서 읽거나, 그럴 수 없으면 출처 줄을 주석으로 단다.
5. **브라우저에서 실습을 실행하지 않는다.** 페이지는 명령을 복사해 줄 뿐이다. 브라우저가 로컬 명령을 실행하게 하는 버튼이나 중계 프로세스를 만들지 않는다.
6. **누구나 쓸 수 있어야 한다.** 모든 위젯은 키보드만으로 조작되고, 색만으로 정보를 전달하지 않으며(등급 배지는 글자 라벨을 함께), `prefers-reduced-motion`을 존중하고, 같은 내용을 표나 글로도 제공한다. 360px 폭에서 가로 스크롤 없이 읽힌다(넓은 표와 출력 블록만 자체 스크롤).

## 3. 구조

```
site/                        # Node 도구는 전부 여기에만 둔다(package.json, lockfile 포함)
├── src/content.config.*     # curriculum/ 을 제자리에서 읽는 로더
├── src/plugins/             # 원고 요소를 컴포넌트로 승격하는 변환(메타 줄, 등급 배지, 명령·출력 짝, 퀴즈, 자기 확인, 링크 재작성)
├── src/components/          # 원고 요소에 1:1로 대응하는 범용 컴포넌트
├── src/widgets/mNN/         # 모듈별 맞춤 위젯과 단위 시험
└── src/i18n/ko.*            # UI 문자열 사전(본문은 원고에서 온다)
tools/sitecheck/             # 내용 동등성·링크·오프라인·접근성 검사기
scripts/guide-up.sh          # 127.0.0.1 에서만 여는 로컬 서버
```

- **프레임워크**: 정적 사이트 생성기 Astro를 쓴다(문서용 테마 Starlight를 먼저 시도한다). 페이지는 기본적으로 JavaScript 없는 HTML로 나오고, 위젯이 놓인 자리만 브라우저에서 스크립트가 붙어 동작한다(Astro는 이런 자리를 "아일랜드", 스크립트가 붙는 일을 "하이드레이션"이라 부른다). 위젯은 작은 UI 라이브러리 Preact로 만들고, 계산 로직은 화면과 분리한 순수 함수로 두어 단위 시험한다.
- **위젯 등록**: 공용 등록 파일을 두지 않는다. 빌드가 `site/src/widgets/mNN/<이름>/` 디렉터리를 찾아 표시의 `<이름>`과 맞춘다. 여러 UI 저자가 같은 파일을 고치지 않게 하기 위해서다.
- **의존성**: `site/package.json`과 lockfile은 환경 구축 엔지니어가 관리한다. UI 저자는 새 패키지가 필요하면 PR 본문에 요청으로 적는다. 브라우저 검사 도구(Playwright, axe-core)도 `site/`의 고정 의존성으로 둔다.
- **확인이 필요한 가정**(시범에서 확인하고, 틀리면 이 문서를 고친다): Starlight가 `site/` 밖의 `curriculum/`을 직접 읽을 수 있다 · Mermaid 다이어그램 109개가 빌드 시점 SVG로 라이트/다크 모두 읽을 만하게 나온다 · 테마 기본값에 외부 요청(글꼴·아이콘)이 없다 · 정적 검색이 한국어에서 쓸 만하다.
- **Node 파일의 위치**: Node 파일은 `site/` 아래에만 둔다. 외부 호스트 정적 검사(`tools/probe/no_external_hosts.py`)는 `tools`·`scripts`·`src`·`curriculum`을 훑는데, 이 네 곳에 Node 파일이 섞이면 결과가 패키지 관리자에 따라 달라진다(npm의 `package-lock.json`은 레지스트리 URL이 들어 있어 M00 `verify.sh`가 실패하고, URL이 없는 lockfile이나 검사 대상 확장자가 아닌 lockfile은 조용히 지나간다). 실습 코드와 사이트 도구를 섞지 않는 편이 검사 범위도, 역할 경계도 분명하다. `tools/sitecheck/`는 Python으로 쓰거나, Node가 필요하면 `site/` 안에 둔다.
- **`site/`의 검사**: `site/`는 위 정적 검사의 기본 범위 밖이다. 대신 `tools/sitecheck/`가 `site/src`의 소스와 빌드 산출물에서 외부 리소스 참조를 검사한다(5장).
- **빌드 때의 외부 접속**: 패키지 설치는 레지스트리에 접속한다. 이것은 빌드하는 쪽(에이전트·CI)에만 생기는 접점이며, 실습의 "외부 호스트에 닿지 않는다"(AUTHORING 규칙 11)와는 별개다. lockfile로 버전을 고정하고, 빌드 **산출물**은 3장·5장의 검사로 외부 요청 0건을 보장한다.
- **한국어**: `lang="ko"`, 본문 `word-break: keep-all`. 공용 UI 문자열(탐색, 퀴즈·모의고사 단추, 안내 문구)은 사전 한 파일에 모은다. 위젯 하나에서만 쓰는 문구는 그 위젯 폴더 안에 둔다 — 사전은 공용부라 UI 저자가 고칠 수 없고, 여러 저자가 같은 파일을 고치면 충돌한다.
- **상태 저장**: 진행 상태·퀴즈 답은 브라우저 `localStorage`에만 둔다. 저장이 막힌 환경에서도 페이지는 정상 동작해야 하고, JSON 내보내기/가져오기를 제공한다.

## 4. 원고 요소와 화면의 대응

원고는 고치지 않고 빌드 때 자동으로 승격한다.

| 원고 요소 | 화면 |
|---|---|
| 레슨 둘째 줄 `> 도메인 · 예상 시간 · 실습 등급` | 메타 칩. 등급은 🟢/🟡/🔴에 글자 라벨과 범례를 더한다. 등급 칸은 레슨의 절반가량이 하나의 등급이 아니라 실습별로 나뉜 값이나 "—"이므로, 변환기는 원문을 잃지 않고 그대로 보여 줄 수 있어야 한다 |
| `bash` 코드 블록과 바로 뒤의 라벨 없는 블록 | 복사 버튼이 달린 명령 + "기록된 실제 출력" 패널. 뒤따르는 출력 블록이 없는 `bash` 블록은 명령만 보여 준다 |
| Mermaid 블록 | 빌드 시점 SVG(라이트/다크). 클라이언트 JS 없음. 다른 코드 블록 **안에** 출력으로 실린 Mermaid 텍스트(M02 레슨 2의 예)는 그림으로 바꾸지 않고 출력 그대로 둔다 |
| 퀴즈의 문항·보기·`<details>` 해설 | 채점되는 문항 카드, 모듈 통과 기준(80%) 표시 |
| 레슨 "스스로 확인"의 `<details>` | 답 가리기/펼치기 |
| `mock-exam/questions.md` + `answer-key.md` | 시험 모드(130분 타이머, 표시해 두기, 복수 응답, 도메인별 점수, 72% 기준). 답안은 `answer-sheet.txt` 형식으로 내보내 `grade.py`와 호환된다 |
| lab·sdk 파일로 가는 상대 링크 | 빌드 때 실제 파일을 읽어 넣은 소스 보기 + 실행 명령 복사 |
| `capstone-self-check.md`의 표 | 상태가 저장되는 체크리스트 |
| 치트시트의 표 | 반응형 표 + 인쇄 스타일 |

- `grade.py`는 지우지 않는다. 터미널 경로이자 사이트 채점의 기준이다(사이트의 채점 결과는 `grade.py`와 같아야 한다).
- **맞춤 위젯**은 원고에 한 줄 표시로 넣는다: `<!-- widget: <이름> -->`. GitHub 렌더링에는 보이지 않고 원고는 유효한 Markdown으로 남는다. 표시가 가리키는 위젯이 없으면 빌드가 실패한다. 표시 줄을 원고에 넣는 것은 그 위젯을 만드는 UI 저자의 몫이며(AUTHORING 1장의 "자기 역할이 아니면 수정하지 않는다"에 대한 유일한 예외), 원고의 다른 부분은 건드리지 않는다. 표시 줄은 빈 줄로 둘러싼 독립된 줄로 넣고, `bash` 블록과 그 출력 블록 사이나 표·목록 안에는 넣지 않는다.
- 원고에 `<!-- external-host-ok: ... -->` 표시가 달린 블록은 그대로 보여 준다(표시는 화면에 내지 않는다).

## 5. 검증 (사이트 PR의 검증자 체크리스트)

[AUTHORING.md 6장](./AUTHORING.md)의 항목에 더해, `site/`나 `tools/sitecheck/`를 바꾸는 PR은 아래를 모두 만족해야 한다.

- [ ] 깨끗한 체크아웃에서 lockfile 고정 설치와 빌드가 성공한다(빌드가 Mermaid 파싱 검사를 겸한다).
- [ ] 내용 동등성 검사 0건: 페이지마다 제목, 모든 코드 블록(바이트 단위), 표의 행·열 수가 원고와 같다.
- [ ] 퀴즈 정답이 원고와 같고, 모의고사 채점이 `grade.py`와 같은 결과를 낸다.
- [ ] 빌드 산출물의 내부 링크와 앵커가 모두 유효하다.
- [ ] 오프라인 검사 0건: 헤드리스 브라우저에서 루프백 밖 요청을 모두 차단·기록하고 대상 페이지를 열었을 때 기록이 없다. 산출물 텍스트에도 외부 리소스 참조가 없다.
- [ ] 접근성 자동 검사를 통과하고, 키보드만으로 퀴즈와 위젯을 끝까지 조작할 수 있다(키 입력만 쓰는 브라우저 자동화 스크립트 `site/tests/keyboard.mjs`로 확인하고, 새 위젯을 만든 PR은 그 조작을 이 스크립트에 더한다).
- [ ] 라이트/다크 × 데스크톱/360px 화면을 검증자가 직접 열어(스크린샷) 깨진 곳이 없음을 확인한다.
- [ ] 위젯의 수치가 원고의 해당 줄과 같고, 모형에는 "모형" 표시가 있다. 위젯 로직의 단위 시험이 통과한다. 모형의 규칙을 AWS 공식 문서와도 대조한다(경계값으로 모형 함수를 직접 불러 본다) — 원고와 같아도 원고가 틀렸거나 조건을 빠뜨렸을 수 있다. 모형이 정하지 못하는 경우는 판정하지 않되, 위젯이 가르치려는 대표 사례는 판정이 나와야 한다.
- [ ] 표의 칸 내용이 옆 칸과 겹치지 않고, 본문 폭을 넘는 표에는 스크롤할 수 있다는 표시가 있다(`tables` 관문). 표의 줄바꿈 방식을 바꾼 PR은 검증자가 표 칸을 복사해 원문과 같은지(줄바꿈용 글자가 섞이지 않는지) 직접 확인한다 — 관문은 이것을 보지 않는다.
- [ ] 로컬 서버가 `127.0.0.1`에만 바인드되고, `site/node_modules`가 없는 갓 받은 저장소에서 `scripts/guide-up.sh`가 끝까지 뜬다(공용 스크립트나 의존성을 건드린 PR).
- [ ] 원고에 위젯 표시 줄만 넣었다면 동등성 검사와 외부 호스트 정적 검사로 충분하다. 그 밖에 원고나 lab을 건드렸다면 해당 모듈 `verify.sh`가 통과한다. `site/` 밖에 Node 파일이 없고 외부 호스트 정적 검사가 0건이다.
- [ ] `tools/sitecheck/sitecheck.py all`과 `parity --pages all`의 출력이 PR 본문에 있고, 검증자가 다시 돌려 같은 결과를 얻는다. `all`은 기본으로 전 페이지를 본다(약 9분). 시범 페이지만 보던 때에는 범위 밖 페이지의 문제를 놓쳤다(원고의 `\~`를 검사기가 풀지 못한 오탐, `docs/` 페이지의 이름 없는 체크 상자, 표 칸 겹침이 그렇게 지나갔다). `--pages pilot`이나 경로 목록은 고치는 도중에만 쓰고, PR에는 전 페이지 결과를 싣는다. 검사를 시험하려고 심는 가짜 주소는 `.invalid`나 루프백만 쓴다.

검증자는 작성자와 다른 에이전트여야 하고, 판정 형식은 AUTHORING 6장과 같다.

## 6. 역할과 브랜치

[AGENTS.md](./AGENTS.md)의 역할 표에 등록한다. 요약:

| 역할 | 브랜치 접두사 | 담당 |
|---|---|---|
| 설계자(메인 세션) | `architect/` | 이 문서와 `docs/`의 설계 문서 |

P1의 M06 시범 위젯과 합쳐 M00\~M13에 14개), 진행 추적을 전 모듈로 넓혔으며(공용 구현 `site/src/progress/`, 모듈 README의 표시 줄 `progress-tracker`), 모의고사에 시험 중 정답 링크 숨김과 응시 기록을 더했다. 위젯마다 `keyboard.check.mjs`를 두면 `keyboard` 관문이 찾아서 돌린다(M06 시범 위젯만 `site/tests/keyboard.mjs`가 직접 조작한다). - P1~P3은 `site/`·`tools/sitecheck/`·`scripts/guide-up.sh`를 더하고 원고에는 GitHub에서 보이지 않는 위젯 표시 줄만 넣으므로, 기존 학습 경로(Markdown + 터미널)에 영향이 없다. P4는 PR 하나를 되돌리면 원래대로 돌아간다.
- **P1이 시험하는 것**: 원고가 자동 변환이 될 만큼 규칙적인가(변환기를 전체 원고에 보고 모드로 돌려 실패율을 잰다 — "직접 해 보기 (2) — …" 같은 변형 제목이 이미 있다) · 3장의 가정들 · 검증 에이전트가 5장을 실제로 수행할 수 있는가(걸린 시간과 놓친 것을 기록한다).
- **P5를 만든다면**: 브라우저에서 에뮬레이터를 직접 부르는 방식은 쓰지 않는다. 설계 때 실행 중인 에뮬레이터 하나에 확인한 바로는 `GET /__admin/health` 응답에 CORS 허용 헤더가 없었고, 브라우저가 본 요청 전에 보내는 사전 확인 요청(`OPTIONS`)에는 404가 돌아왔다(다른 경로는 확인하지 않았다). 사설 CA 신뢰와 요청 서명 문제도 있다. 로컬 중계 프로세스가 필요하며, `require_emulator()`를 먼저 호출하고, `127.0.0.1`에만 바인드하고, Host 헤더를 검사하고, 조회 API 허용 목록만 제공한다. 공개 배포된 페이지에서는 동작하지 않는다.
